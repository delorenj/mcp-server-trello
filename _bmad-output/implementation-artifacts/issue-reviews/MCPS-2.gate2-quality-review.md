## Concrete positions on the four action items

### Q1 — Is the duplication the correct trade?

**No. Factor it — and doing so does not violate the constraint.**

The block now appears **five** times in `src/trello-client.ts`:

| Line | Method |
|------|--------|
| `:670` | `getChecklistItems` |
| `:710` | `addChecklistItem` |
| `:755` | `findChecklistItemsByDescription` |
| `:878` | `getChecklistByName` |
| `:794` | `resolveChecklistsInScope` *(new)* |

I diffed the helper against the inline block line by line:

- **Card path** — identical (`GET /cards/{id}` with `params: { checklists: 'all' }`, then `.checklists || []`).
- **`McpError`** — identical `ErrorCode.InvalidParams` and identical message string `'No board ID or card ID provided and no active board set'`.
- **Board path** — the **only** delta: helper returns `response.data || []`; the inline version does `checklists = response.data` unguarded.

That delta is reachable only when a 200 response carries a null body. In that case today's `getChecklistItems` throws `TypeError: checklists is not iterable` at its `for...of`, whereas the helper returns `[]`.

**So the honest read:** "no behavior change to `getChecklistItems`" is a constraint about *observable, tested* behavior — match semantics, item ordering, and the missing-board error. The helper preserves all three **exactly**. The lone delta converts an unreachable crash into an empty array; no test asserts that `TypeError`, and no caller can depend on it.

**Exact refactor (follow-up PR, mechanical, four call sites):** in each of `getChecklistItems`, `addChecklistItem`, `findChecklistItemsByDescription`, and `getChecklistByName`, delete the `let checklists: TrelloChecklist[];` declaration and the whole if/else block, and replace with:

```ts
const checklists = await this.resolveChecklistsInScope(cardId, boardId);
```

Everything downstream (`.filter`, `.find`, `for...of`) is untouched. The existing suite is the safety net.

**Do not** add an options flag to the helper to preserve the null-body `TypeError` bit-for-bit — that would be uglier than the duplication it removes.

**Not a merge blocker for this PR.** The author did the right half of the job; the other half is a clean standalone change.

### Q2 — Do the health updates mask something they should surface?

**Yes — but the masking is correct at the status level and wrong at the metadata level.**

**Keep `HealthStatus.HEALTHY`.** I would actively push back on anyone wanting to degrade it. That probe tests whether the checklist API is reachable; a board with no acceptance-criteria checklist is a fact about board content, not about server health. Collapsing to zero is the right default, and it is applied consistently across both files.

**The real problem is one layer up.** `acceptance_criteria_count: 0` at `src/health/health-monitor.ts:394` is now **ambiguous in exactly the way this ticket exists to eliminate** — it means either "no AC checklist exists" or "the AC checklist exists and is empty." The client can finally distinguish those two; the health output throws the distinction away. The ticket removed the ambiguity at the tool boundary and it silently reappeared in the health surface.

*Fix (one line each, no schema break — both are free-form bags):*
- `src/health/health-monitor.ts:394` — add `acceptance_criteria_found: criteria.found` to the `metadata` object.
- `src/health/health-endpoints.ts:264` — add the equivalent to `results.statistics`.

Cheap, non-breaking, and it preserves a diagnostic the codebase just gained. Worth doing.

### Q3 — Real defect or theoretical?

**Theoretical today. Resolve it by *deleting* the guard, not by adding more.**

`src/types.ts:128` declares `TrelloChecklist.name: string` — non-optional — and Trello always returns a name for a checklist. So `checklist.name || ''` at `src/trello-client.ts:839` defends against something the type system asserts cannot happen. It is also inconsistent with the file: all four sibling methods do a bare `checklist.name.toLowerCase()` with no guard whatsoever.

The indefensible part is the **half-guarded** state. Line `:839` implies distrust of the type, while `:853` (`matchedChecklistName: matching[0].name`) and `:865` (`availableChecklists: checklists.map(c => c.name)`) trust it completely. If that distrust were warranted, `availableChecklists` would return `[null]` against a declared `string[]`, and a consumer calling `.toLowerCase()` on an entry would crash. One file, two contradictory assumptions about the same field.

*Fix:* drop `|| ''` at `:839`. That resolves the contradiction in the direction of the repo's existing convention and removes the type lie without adding noise.

*If the team actually believes the name can be null*, then the **type** is wrong (`name: string | null`) and all four sibling methods are latent crashes — a substantially larger finding than anything in this diff, and one that should be filed separately.

### Q4 — Bloat or justified?

**Bloat. Here are the numbers.**

Measured across the 51 single-quoted `description:` literals in `src/index.ts`:

| Metric | Chars |
|---|---|
| Median | **49** |
| Mean | **86** |
| Previous longest (`update_list_position`, `:491`) | **279** |
| **This description (`:1180`)** | **708** |

That is **2.5× the previous maximum** and **~14× the median**, shipping into every agent's context every session alongside 56 other tools.

Roughly half of it re-states what the payload already makes self-evident. An agent receiving `{found: false, reason: "...", availableChecklists: [...]}` does not need advance warning that a `reason` field exists — the `reason` string itself already names every alias that was tried. Likewise "A matched-but-empty checklist returns `found: true` with `items: []`": the agent will simply observe that. Description text should carry only what is **not** recoverable from the response.

*Concrete replacement (~240 chars), keeping the alias set and the precedence rule — the two facts genuinely not discoverable from a response:*

```
Get a card's (or board's) acceptance criteria. Matches a checklist named
"Acceptance Criteria", "AC", "DoD", or "Definition of Done" (case-insensitive);
first match in that order wins. Returns a {found: true|false} union; read
reason when not found.
```

That is a ~66% cut with no loss of actionable information.

## 3. Assessment

**Mergeable with follow-ups.**

The core engineering is sound. The discriminated union is well-formed and genuinely ergonomic — the tests narrow it six times without a single cast, which is the proof that matters. The alias set is data rather than branching, the tie-break is deterministic and documented, and the not-found `reason` derives from the same constant it describes, so it cannot go stale. `resolveChecklistsInScope` moves the file toward less entropy rather than more. It typechecks clean, 78/78 tests pass, and it reads like its neighbors; the one place it diverges from repo convention — heavy JSDoc where `CheckList`/`CheckListItem` have none — is a divergence in the right direction.

Nothing here is a blocker. The single item I would want landed before or immediately after merge is **I-1 (doc drift)**: this is a breaking change to a documented tool's response shape in a repo that maintains a rigorous changelog, and shipping with `README.md` still describing the old single-name behavior is the kind of drift that costs a downstream user an hour. **I-4** is cheap enough to fold into this PR if the author is still in the file. **I-2**, **I-3**, and the one-line fixes from Q2 and Q3 are all follow-up-shaped and can ship independently.
